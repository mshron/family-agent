# Phase 1 — Feel test: what is running, and how to use it

Status: **deployed and verified** (2026-10-03), rebuilt on **pi-durable**
(`@earendil-works/pi-durable`). The design lives in
`docs/memos/hetzner-consolidation.md` (Phase 1 section); the rules that make
running bare acceptable are listed there and repeated below.

## What is running

On the code box (`128.140.54.129`), under `/opt/family-agent/`:

| Piece | What it is |
|---|---|
| `fa-gateway` container | The whole substrate: a pi-durable `Harness` plus the Zulip bridge. One event queue long-poll; one conversation per `(stream, topic)`; model calls (OpenRouter keys live only here); posts replies, spoilers, and command responses. |
| `fa-exec-<hash>` containers | One per active conversation. Tools (`bash`, `read`, `write`, `edit`, `grep`) run in it via `docker exec`. It mounts the channel workspace at `/workspace`. No keys, no network tools. Removed after 30 min idle. |
| `durable/` | The pi-durable store (JSONL): every conversation's entries, tasks, submissions, and documents. Survives restarts; `boot scan` rebuilds the topic→conversation map. |
| `workspaces/<stream>/` | One git repo per channel: `AGENTS.md` conventions, `notes/`, `docs/`, `memory/`. Sessions commit here. |
| `.env` | Secrets, mode 600. Generated by `deploy/push-secrets.sh` from local sources. |

The Zulip bot is the existing "Nanobot" bot user, on the private stream
**`scratch`**.

## How it behaves

- Every topic in `scratch` is one conversation with full coding tools.
- **Thinking indicator.** The bot reacts to your message with :eyes: while the
  run is live and removes the reaction when the reply posts.
- **Attachments.** Files and photos posted in Zulip are downloaded into the
  channel workspace's `uploads/` directory before the turn starts; the
  message text the agent sees carries the local paths.
- **Tool-call spoilers.** Each tool call posts one collapsible spoiler block
  in the topic (````spoiler <tool> — <args> ... result`). The gateway filters
  its own posts out of ingestion, so agents never see these in their
  transcript; they are for you.
- **General chat.** A message sent with subject `general chat` (what the
  web UI does for topic-less compose) gets auto-named: a cheap model call
  picks a 2–4 word name, the thread is renamed retroactively (messages
  after the last burst move into the new topic), and a note is posted.
- **Thread tools.** The agent can `spawn_thread` (new topic, independent
  task, replies there) and `fork_thread` (new topic carrying this
  conversation's full history). Both post a header so you can see where
  the thread came from.
- **`history_search`.** Channel-scoped search over past conversations
  (all topics, including pre-`/new` ones), with topic names in results.
- **Direct messages.** A DM to the bot is one continuous conversation per
  DM group, and each group gets its own workspace (`workspaces/dm-<user
  ids>`) — memory and notes from one person's DM never surface in another
  person's. Spoilers, reactions, commands, and uploads work there;
  spawn/fork do not (DMs have no topics).
- **Channels.** Membership-driven: any member of the Zulip organization can
  invite the bot to a stream; the bot joins, provisions the channel's
  workspace, and starts watching. `phase1/channels.json` holds only seed
  streams (auto-subscribed at boot) and per-channel tool overrides
  (`tools` replaces, `add` appends to the standard set). Removing the bot
  from a stream stops that channel's poller.
- **mark (markdown preview).** The `mark <file.md>` command registers a
  doc with a preview server on the box and prints a tailnet URL; agents
  post the URL in chat, and the reader (on a tailnet device) gets a live
  preview with click-to-comment review (comments land in
  `<file>.comments.md` beside the doc). Requires Tailscale on the box
  (the sidecar binds only the tailscale address) and
  `MARK_HOST`/`MARK_TOKEN` in `.env`; the sidecar itself is installed on
  the box, not from this repo.
- **Skills.** Two read-only layers mounted into every exec container:
  `/skills` (global) and `/channel-skills` (this channel). Install with
  `phase1/skills/install.sh <git-url-or-path> [--global | --channel NAME]`.
  A `skills` prompt section lists what is available.
- **Search.** `search` and `summarize_url` (Brave today; Kagi when the key
  is available).

## Commands

- `/model auto` — default: a cheap classifier picks flash (GLM-5.3-flash,
  thinking low) or strong (GLM-5.3, thinking high) per message.
  `/model flash` / `/model strong` pin the physical model for the topic.
- `/stats` — entries and spend for the topic's conversation.
- `/new` — the agent writes a handoff note to `notes/`, commits it, then the
  conversation resets. Memory and workspace carry over; `history_search`
  still sees the old one.
- `/compact` — background compaction at the next turn boundary.
- `/stop` — abort the current run.
- Editing or deleting one of your messages is followed by the gateway:
  the latest message re-runs in place (edit re-answers, delete silently
  retracts the turn); an edit or delete further back forks the conversation
  into a new topic that continues from before it (streams only — DMs follow
  latest-message edits only). See `docs/memos/message-editing.md`.

## The rules that make running bare acceptable

No email, no finance repo, no deploy keys. Search results are the only
untrusted text entering a conversation. Phase 2 landed the permission gates
and the audit log (next section); the rotation checklist is in
`docs/memos/phase2-hardening.md` (rotate the Zulip bot key and the
OpenRouter key when the box split happens).
(While debugging the Zulip event API, the bot key appeared in base64 in a
terminal transcript — one more reason to rotate at Phase 2.)

## Phase 2 — permission gates and audit log (live)

The hardening layer runs on the single box now; the two-box split, proxy,
egress lockdown, and rotation are staged as assets plus a runbook in
`docs/memos/phase2-hardening.md`.

- **Rules** live in `phase1/channels.json`. A top-level `permissions.bash`
  map applies everywhere (shipped: `rm -rf /*` and `sudo *` denied); a
  channel's `permissions.tools` map gates named tools. Semantics:
  wildcard patterns (`*` matches anything), **last matching rule wins**, so
  put catch-alls first; unmatched calls are allowed.
- **`push_changes` in #meta is gated**: the gateway posts an approval
  message listing the pending commits; react ✅ to approve, ❌ to deny.
  Only `ZULIP_OWNER_EMAILS` users may approve. Auto-denied after
  `ASK_TIMEOUT_MINUTES` (default 20). Sessions cannot forge approvals —
  they never see reaction events.
- **Audit log**: `/opt/family-agent/audit/audit.jsonl`, one JSON line per
  event (tool decisions and outcomes, pushes, commands, threads,
  boot/shutdown). Gateway-only mount; sessions cannot read it.
- **Fail-open vs fail-closed**: a bug in rule classification fails open
  (logged, audited) so sessions keep working; a failure of the approval
  flow itself blocks the action — no surface, no consent.
- **Pre-deploy checks** (run from `phase1/gateway/`):
  `node scripts/permissions-contract.mjs` and
  `node scripts/permissions-smoke.mjs` (the latter spins a fake model
  server; no network beyond localhost).

## The #meta channel (self-modification)

`meta` is where the system can work on itself. Its workspace is a git clone
of the family-agent repo, so agents there edit real code with the normal
tools, and `push_changes` runs `git push origin main` with a deploy key that
lives only on the box's gateway side (agents can trigger a push, never read
the key). Since Phase 2, the push is approval-gated: the gateway posts the
pending commits in the topic and pushes only after the owner reacts ✅.
A push triggers the GitHub Actions workflow
(`.github/workflows/deploy.yml`) which connects to the box and runs
`phase1/deploy/pull-deploy.sh` (reset the meta clone to `origin/main`, rsync
`phase1/`, redeploy). Secrets stay outside the repo tree on the box.

Two keys, two directions — do not reuse one for the other:

- **Deploy key** (box → GitHub): write access to this repo only. Lives in
  `/opt/family-agent/secrets/push/` on the box; the gateway mounts it
  read-only into a one-shot push container. Agents never see it.
- **CI key** (GitHub runner → box): ssh to `root` on the box. Its private
  half is the `DEPLOY_SSH_KEY` Actions secret; its public half is in the
  box's `authorized_keys`.

`/opt/family-agent` and everything under it is runtime state that exists
only on the box — never in the repo.

### Wiring step 1 — deploy key (run on the box)

```bash
ssh root@128.140.54.129
install -d -m 700 /opt/family-agent/secrets/push
ssh-keygen -t ed25519 -N '' -C 'family-agent meta push' \
  -f /opt/family-agent/secrets/push/id_ed25519
ssh-keyscan -t ed25519 github.com > /opt/family-agent/secrets/push/known_hosts
# verify against GitHub's published fingerprints
# (docs.github.com ... githubs-ssh-key-fingerprints):
ssh-keygen -lf /opt/family-agent/secrets/push/known_hosts
chmod 600 /opt/family-agent/secrets/push/*
cat /opt/family-agent/secrets/push/id_ed25519.pub
```

Then register the public half: repo → Settings → Deploy keys → Add deploy
key → paste → **check "Allow write access"**. With `gh`:
`gh repo deploy-key add <pub-file> --title 'family-agent box' --allow-write`.

### Wiring step 2 — meta workspace = repo clone (run on the box)

```bash
cd /opt/family-agent/workspaces
mv meta meta.skeleton.bak
GIT_SSH_COMMAND="ssh -i /opt/family-agent/secrets/push/id_ed25519 \
  -o UserKnownHostsFile=/opt/family-agent/secrets/push/known_hosts \
  -o StrictHostKeyChecking=yes" \
  git clone git@github.com:mshron/family-agent.git meta
cd meta
git config user.name 'family-agent (#meta)'
git config user.email 'meta@family-agent.local'
git config core.sshCommand "ssh -i /opt/family-agent/secrets/push/id_ed25519 \
  -o UserKnownHostsFile=/opt/family-agent/secrets/push/known_hosts \
  -o StrictHostKeyChecking=yes"
docker ps -q --filter label=family-agent-exec | xargs -r docker rm -f
```

`core.sshCommand` makes every fetch and push from this clone use the deploy
key (the CI deploy's `git fetch` runs as root here). The push container
overrides it with its own `GIT_SSH_COMMAND` environment variable, so both
paths work. No gateway restart is needed; exec containers respawn on demand.

### Wiring step 3 — Actions secrets (run on your machine)

```bash
ssh-keygen -t ed25519 -N '' -f fa-ci-deploy -C family-agent-ci
ssh-copy-id -i fa-ci-deploy.pub root@128.140.54.129
ssh-keyscan -t ed25519 128.140.54.129 > fa-box-known-hosts
gh secret set DEPLOY_SSH_KEY --repo mshron/family-agent < fa-ci-deploy
gh secret set DEPLOY_KNOWN_HOSTS --repo mshron/family-agent < fa-box-known-hosts
gh secret set DEPLOY_HOST --repo mshron/family-agent --body 128.140.54.129
rm fa-ci-deploy fa-ci-deploy.pub fa-box-known-hosts
```

(Or paste the same three values in repo → Settings → Secrets and variables →
Actions.)

### Adding a channel (membership-driven)

Since the membership rewrite, Zulip itself is the source of truth for which
streams the gateway watches. To add a channel from the Zulip app:

1. Create the stream and invite the bot (add an owner to the stream too —
   see the invite gate below).
2. The gateway's control queue receives the `subscription` add event, runs
   the invite gate (an owner must be a subscriber; if `ZULIP_OWNER_EMAILS`
   is configured and none is present, the invite is declined and the bot
   leaves), provisions the workspace (copy of `phase1/workspace/`, git
   initialized) and an empty `skills/<stream>/` dir, starts a poller, and
   posts a greeting in a `family-agent` topic. No deploy involved.
3. If the channel needs tools beyond the standard set, add a
   `channels.<name>` block to `phase1/channels.json` in a normal commit
   (`add` appends tools, `tools` replaces the set, `push: true` enables
   `push_changes`). Watching the stream needs no deploy; new tool sets
   apply to new conversations.

Seed streams (`streams` in `channels.json`, currently `scratch` and
`meta`) are still self-subscribed at boot, and the bot also adds the
configured owners to them. Removing the bot from any stream stops its
poller for that channel.

The old channels.json-driven flow (add stream to the file, deploy, bot
creates it if missing) still works for seeds.

What is still not automatic: tool-set selection for new channels
(deliberately — granting bash/push is a choice), and any ability to grant
itself access to streams nobody invited it to.

### Dependencies and upgrades

`package.json` pins `chord`, `pi-ai`, and `pi-durable` to exact versions, with
a committed `package-lock.json`; the image builds with `npm ci`. This is
load-bearing: an earlier unpinned setup resolved `^1.0.0` at build time, a
rebuild silently picked up pi-durable 1.0.4, and its stricter `onOutput`
contract crashed the gateway on every bash call with output. Upgrading is now
a deliberate act:

1. Bump the pins, regenerate the lockfile, build a test image.
2. Run the contract check:
   `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v <repo>/phase1/gateway/scripts/onoutput-contract.mjs:/app/check.mjs:ro -w /app fa-test node check.mjs`
3. Deploy, then exercise bash in a channel.

### Semantics to know

- Every deploy resets the meta clone to `origin/main`. Work that is
  committed but not pushed is discarded by the next deploy; uncommitted
  work is lost. Commit, then `push_changes` (and the owner approves).
- Every deploy restarts the gateway. In-flight runs complete in the durable
  store but their replies may not post; ask the user to resend if one is
  missing.
- `DEPLOY_SSH_KEY` grants root ssh to the box, and anyone who can edit the
  workflow can read it out. Protect `main` (Settings → Branches → branch
  protection) so only you can push to it.

### Verify

Push any commit to `main` and watch it land
(`gh run watch` or Actions → deploy), then on the box:
`docker logs fa-gateway` and `git -C /opt/family-agent/workspaces/meta log -1`.

## Known limitations

- Credentials sit in the gateway environment until the box split: no
  proxy, no egress lockdown yet. Exec containers get none of them (no keys,
  and they never see `.env`); the credential proxy config and the egress
  script are staged in `deploy/proxy/` and `deploy/egress-lockdown.sh`.
- A run interrupted by a restart while waiting on an approval resumes but
  may refuse on timeout (the approval message is reused, not duplicated);
  interrupted runs' replies may not post (existing gap).
- Old (pre-migration) pi session files were not imported: topics that had
  history in the RPC gateway start fresh in the durable store. The
  workspace, memory, and notes carry the durable parts.
- If the gateway restarts mid-run, the run completes durably but its reply
  is never posted to Zulip (no delivery retry yet).
- Replies over 9000 chars are truncated with a pointer to the workspace.
- One channel (`scratch`) is wired; more channels is a one-line change
  (`SCRATCH_STREAM` is a single value today).
